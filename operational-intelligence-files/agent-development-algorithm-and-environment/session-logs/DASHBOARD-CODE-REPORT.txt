SECTION 1 — WHAT THE CODEBASE PRODUCES TODAY (DATA INVENTORY)
-------------------------------------------------------------------------------

This section lists every data event the system currently emits, where it goes,
and the exact schema shape. This is the raw material for a dashboard.


1.1  CONVERSATION LOG EVENTS
     Source file:  server/routes/log.js
     Endpoint:     POST /api/log/conversation
     Current sink: console.log (stdout only)
     Persistence:  NONE — data is lost when server restarts
     SEC status:   SEC-11 OPEN — PHI text field, stdout is not HIPAA-compliant

     Schema (as written to stdout):
     {
       "ts":        ISO 8601 timestamp,
       "sessionId": string (max 64 chars),
       "clientId":  string (max 32 chars),
       "turn":      integer (which turn in the conversation),
       "role":      "user" | "assistant",
       "state":     one of: IDLE / GREETING / DISCOVERY / INTENT_DETECTED /
                    FLOW_GENERAL / FLOW_SERVICE_{INTENT_KEY} / LEAD_CAPTURE /
                    BOOKING_CONFIRMATION / CLOSING / OBJECTION / FALLBACK / ENDED,
       "intent":    e.g. "GENERAL_CONSULT" / "DENTAL" / "FOLLOW_UP" / "URGENT_CARE",
       "text":      string (max 500 chars, may contain patient PHI)
     }

     Note: The endpoint validates sessionId, role, and text are present.
     The 'state' and 'intent' fields are optional but sent by app.js.


1.2  LEAD CAPTURE RECORDS
     Source file:  js/modules/lead-capture.js — LeadCapture.save()
     Current sinks:
       (a) localStorage — key format: "av_leads_v1:{normalized_company_name}"
                          Example key: "av_leads_v1:medvoice_clinic"
                          This is browser-local. Not accessible server-side.
       (b) Webhook dispatch — event type "LEAD_CAPTURE" sent to webhook_url
           (via WebhookDispatcher, stored in IndexedDB outbox first)

     Schema (as stored in localStorage and sent via webhook):
     {
       "name":               string | null,
       "patient_type":       "new" | "returning" | null,
       "dob":                string | null,
       "reason_for_visit":   string | null,
       "insurance_provider": string | null,
       "insurance_id":       string | null,
       "urgency":            string | null,
       "contactMethod":      "phone" | "email" | null,
       "client_id":          string (company_name from config),
       "capturedAt":         ISO 8601 timestamp,
       "completeness":       integer 0–100
     }

     Completeness scoring (from lead-capture.js lines 138–147):
       name:               +30 points
       patient_type:       +20 points
       reason_for_visit:   +25 points
       dob:                +15 points
       insurance_provider: +10 points
       Maximum total:       100 points

     Capture order (from _captureOrder, line 91):
       name → patient_type → dob → reason_for_visit → insurance_provider


1.3  WEBHOOK OUTBOX EVENTS
     Source file:  js/services/webhook-dispatcher.js
     Storage:      IndexedDB (outbox-db.js)
     Delivery:     HTTP POST to config.webhook_url with HMAC-SHA256 signature

     Outbox item schema:
     {
       "id":              auto-increment integer (IndexedDB key),
       "client_id":       string,
       "webhook_url":     string (captured at dispatch time),
       "event_type":      "LEAD_CAPTURE" (others possible in future),
       "data":            object (the lead data payload),
       "timestamp":       ISO 8601,
       "idempotency_key": UUID v4,
       "status":          "PENDING" | "PROCESSING" | "DEAD_LETTER",
       "attempts":        integer (0 to 5),
       "lastAttempt":     epoch milliseconds
     }

     Stats available via webhookDispatcher.getStats() (lines 279–288):
     {
       "total":       integer,
       "pending":     integer,
       "processing":  integer,
       "deadLetter":  integer,
       "initialized": boolean
     }

     Retry logic: Exponential backoff with full jitter.
     Base: 1s. Max: 1 hour. Dead-letter after 5 failures.
     No server-side API endpoint exists for these stats yet.


1.4  STATE MACHINE CONTEXT (PER SESSION, IN-MEMORY ONLY)
     Source file:  js/state-machine.js — ConversationStateMachine
     Current sink: In-memory only. Not persisted anywhere.

     Context shape (from reset() method, lines 126–187):
     {
       "state":            current STATES value,
       "intent":           string | null,
       "intentStrength":   0.0–1.0 float,
       "urgency_level":    "low" | "medium" | "high",
       "engagementScore":  0–100 integer (starts at 50),
       "conversationGoal": "identify_problem" | "explore_context" |
                           "position_solution" | "capture_lead" | "close",
       "contextMemory":    array of memory objects,
       "leadData":         { name, patient_type, dob, reason_for_visit,
                             insurance_provider, insurance_id, urgency,
                             contactMethod },
       "history":          array of { from, to, turn, timestamp, data },
       "flowStep":         integer,
       "discoveryDepth":   0–3 integer,
       "fallbackCount":    integer,
       "turnCount":        integer,
       "previousState":    string | null,
       "activeFlow":       string | null
     }

     Engagement scoring (from adjustEngagement / getEngagementLevel):
       score >= 75 → "high"
       score 40–74 → "medium"
       score < 40  → "low"

     Lead completeness (from getLeadCompleteness, lines 388–398):
       name:               +25
       patient_type:       +15
       reason_for_visit:   +25
       dob:                +15
       insurance_provider: +10
       urgency:            +10
       Maximum total:       100 (note: different weights than LeadCapture module)

     All state transitions are recorded in context.history with timestamps.
     This means a full replay of any conversation is theoretically possible
     — but only while the page session is alive.


1.5  EMERGENCY DETECTOR EVENTS
     Source file:  js/modules/emergency-detector.js
     Current sink: console.warn only (line 102)
     Persistence:  NONE

     Scan result shape (from scan() return, lines 103–109):
     {
       "detected":      boolean,
       "response":      string | null (display response),
       "voiceResponse": string | null (TTS response),
       "pattern":       string | null (regex pattern that matched)
     }

     Additional state: this._triggerCount (integer, per-session count)

     Categories monitored: Cardiac, Respiratory, Neurological/Stroke,
     Trauma/Severe Injury, Pediatric, Direct emergency declarations (911, etc.)
     Total patterns: 27 regex patterns (lines 25–64)


1.6  CALENDAR BOOKING EVENTS
     Source file:  server/routes/calendar.js
     Endpoints:    POST /api/calendar/check  (availability query)
                   POST /api/calendar/book   (create event)
     Current sink: Google Calendar (event created if credentials valid)
     Status:       BLOCKER-01 OPEN — never tested with real credentials

     Booking payload (from /api/calendar/book, lines 57–67):
     {
       "calendar_id":  string (Google Calendar ID),
       "startTime":    ISO datetime,
       "endTime":      ISO datetime,
       "patientName":  string,
       "reason":       string,
       "leadId":       string
     }

     Success response: { success: true, eventId: string }
     The event is titled "MedVoice: {patientName}" in Google Calendar.


1.7  LLM HEALTH STATUS
     Source file:  server/routes/llm-proxy.js — GET /api/llm/health
     Response:     { "available": boolean, "endpoint": "configured" }
     Timeout:      3 seconds (AbortController)
     Checks:       Pings OLLAMA_ENDPOINT/api/tags


1.8  SERVER HEALTH
     Source file:  server/routes/health.js — GET /health
     Response:     { "status": "UP", "timestamp": ISO, "version": "1.0.0" }


1.9  CLIENT CONFIGURATION

     Returns:      Full config JSON with secrets injected from env vars

SECTION 2 — THE DATA GAP: WHAT IS MISSING FOR A DASHBOARD TO WORK
-------------------------------------------------------------------------------

This is the critical section. The codebase produces rich data, but almost none
of it is persisted in a way a dashboard can query. Here is the gap table:


  DATA TYPE               | PRODUCED BY           | CURRENT SINK     | GAP
  ─────────────────────────────────────────────────────────────────────────────
  Conversation turns      | app.js → /api/log     | stdout           | No DB
  Lead records            | lead-capture.js       | localStorage     | Browser-only
  Session metadata        | state-machine.js      | In-memory        | Lost on close
  Emergency events        | emergency-detector.js | console.warn     | No storage
  Webhook queue stats     | webhook-dispatcher.js | IndexedDB        | No API endpoint
  Calendar bookings       | calendar.js           | Google Calendar  | No local record
  Engagement scores       | state-machine.js      | In-memory        | Lost on close
  State transition history| state-machine.js      | In-memory        | Lost on close
  LLM health              | llm-proxy.js          | Ephemeral HTTP   | Needs polling
  Server health           | health.js             | Ephemeral HTTP   | Needs polling


What this means in plain terms:

  Right now, if 50 patients call in a day, the clinic sees NOTHING after the
  calls end. No record of who called. No record of what they wanted.
  No record of whether leads were captured. It all goes to stdout.

  A dashboard built against the CURRENT data layer would only be able to show:
    - LLM health (live ping)
    - Server health (live ping)
    - Configuration (read from config files)
    - Whatever is still in the current browser session's localStorage

  That is not useful. The data layer must be fixed first.

SECTION 5 — DASHBOARD TYPE RECOMMENDATION
-------------------------------------------------------------------------------

RECOMMENDED TYPE:
  Clinic Admin Dashboard — Single Page Application
  Primary user: Clinic manager / practice administrator / front desk staff
  Secondary user: Developer (system health panel)

WHY THIS TYPE AND NOT OTHERS:

  Option A — Real-time monitoring dashboard (call center style)
    Rejected because: Voice channel is web widget, not Twilio phone calls yet.
    BLOCKER-01 means phone calls haven't been tested. There is nothing real-time
    to monitor at this stage. Build this in Phase 2 when Twilio is live.

  Option B — SaaS multi-tenant admin panel
    Rejected because: Only one client config exists (medical-clinic.json).
    Multi-tenancy UI is overhead with zero near-term benefit. Revisit when
    the product has 3+ paying clients.

  Option C — Patient-facing portal
    Rejected because: Patients interact through the voice widget, not a portal.
    No patient authentication system exists. Out of scope.

  Option D — Clinic Admin Dashboard (RECOMMENDED)
    Accepted because:
      - Matches the actual users (clinic staff checking leads, call logs)
      - Maps directly to the data the system already produces
      - Scoped to what is buildable in the next sprint
      - Enables the most important business question: "Who called and what did
        they want?" which is currently completely invisible to the clinic

PRIMARY CONSUMER:
  Clinic manager who needs to answer:
    1. How many people reached out to Aria today?
    2. What service did they want?
    3. Did we capture their name and reason for visit?
    4. Were there any emergency situations?
    5. Is the AI system working right now?
